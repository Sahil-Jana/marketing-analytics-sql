# SQL-Driven Full-Funnel Marketing Profitability Analysis

> **Status: Phase 4 of 5 complete.** Schema, synthetic dataset, core
> acquisition/CAC/ROAS/marketing-contribution analytics, cohort/retention
> analysis, observed LTV, RFM segmentation, LTV:CAC, profitability, a
> budget-allocation framework, and a build-ready 3-page Power BI dashboard
> spec are implemented and validated. Final resume/interview material is
> **not yet built** (Phase 5).

## Objective

Build a SQL-driven analysis of the marketing funnel end to end:
**Acquisition → Conversion → Retention → LTV → CAC → ROAS → Profitability
→ Business Recommendations**, using actual customer purchase behavior
rather than a pre-existing/assumed churn or quality label.

This is a portfolio project built on a fully synthetic, deterministically
generated dataset (see below). **No real business, customers, or revenue
are represented, and no real-world business impact is claimed.**

SQL is organized in layers so each query file states its own business
question and assumptions rather than relying on a separate tool (dbt was
evaluated in Phase 1 and skipped as unnecessary overhead at this scale -
plain, well-organized `.sql` files carry the same story in an interview).

## Database Schema

Six tables, each earning its place against a specific analysis:

| Table | Purpose |
|---|---|
| `channels` | Marketing channel dimension (Paid Search, Paid Social, Email, Organic Search, Referral, Affiliate) |
| `campaigns` | Campaign metadata; FK to `channels` |
| `daily_campaign_spend` | Daily spend/impressions/clicks per campaign; FK to `campaigns` |
| `leads` | Acquisition-funnel events; FK to `campaigns`, optional FK to `customers` on conversion |
| `customers` | One row per acquired customer; `first_campaign_id` records first-touch attribution |
| `orders` | Dated, multi-row-per-customer revenue events; FK to `customers` |

Relationships: `channels → campaigns → {leads, daily_campaign_spend}`,
converted `leads → customers → orders`.

There is deliberately no `churn_probability` or similar pre-computed
label anywhere in the schema - the RFM segmentation below is derived
entirely from observed `orders` behavior (recency/frequency/monetary),
which is the main structural difference from the reference project this
was redesigned from.

## Synthetic Dataset

Generated by `sql/02_seed/generate_data.py` using only the Python
standard library (`random`, seeded with `42`) - fully deterministic,
re-running it produces byte-identical CSVs. Channels have different
underlying cost-per-lead, conversion rate, average order value, and
repeat-purchase behavior, so campaigns and channels are believably
different from each other rather than randomly interchangeable; nothing
about the distributions is tuned to be extreme.

Actual generated volumes (window: 2025-01-30 to 2026-06-28, ~18 months):

| Table | Rows |
|---|---|
| channels | 6 |
| campaigns | 40 |
| daily_campaign_spend | 3,611 |
| leads | 104,333 |
| customers | 25,064 |
| orders | 72,002 |

## Setup

Requires Docker only (no local Postgres/Python packages beyond the
standard library).

```bash
./setup.sh
```

This starts a Postgres 16 container, creates the schema, regenerates the
synthetic CSVs, loads them via server-side `COPY`, builds the staging/
mart/Power-BI-export views, and runs the full data-quality validation
suite. All steps can also be run individually - see `setup.sh` for the
exact commands. Re-verified in Phase 4 with a full clean-slate rebuild
(`docker compose down -v && ./setup.sh`) - reproduces identically from
nothing.

To build the dashboard once the database is running, follow
`powerbi/DASHBOARD_BUILD_GUIDE.md` (connects Power BI Desktop to
`localhost:5432`, database `roas`, credentials `roas`/`roas`).

## KPI Definitions & Attribution Assumptions

**Attribution: first-touch.** A customer's acquisition and all revenue
they generate are credited to `customers.first_campaign_id` - the
campaign whose lead converted them. There is no multi-touch event table
in this schema, so first-touch is the simplest assumption the data can
actually support; it is documented, not assumed silently.

- **Conversion rate** = converted leads ÷ total leads, computed directly
  from `leads` row counts (a real funnel, not an assumed rate).
- **CAC** = total campaign spend ÷ customers acquired by that campaign.
  Does not include creative/agency/tooling cost, and says nothing about
  acquired-customer quality (see ROAS/LTV for that).
- **ROAS** — reported as two separate, explicitly labeled numbers so
  spend and revenue windows are never silently mixed:
  - `roas_in_window` = revenue from orders placed during the campaign's
    own active dates ÷ campaign spend.
  - `roas_lifetime` = all revenue to date from that campaign's acquired
    customers ÷ campaign spend.
- **Marketing contribution** = attributed revenue − marketing spend.
  This is **not company profit** - it excludes COGS, fulfillment,
  payroll, and all other operating costs; it is a marketing-efficiency
  signal only.
- **Customer revenue foundation** = observed cumulative `orders` revenue
  per customer. This is a foundation for Phase 3 LTV/cohort work, not a
  finished LTV figure.

## Phase 3: Cohort, Retention, LTV, RFM, LTV:CAC, Profitability

All Phase 3 analysis is built from three reusable marts:
`mart_customer_cohort_spine` (a bounded customer x month spine, not an
unbounded cartesian product - see file comments), `mart_customer_month_activity`
(the spine joined to monthly order activity), and `mart_customer_rfm`
(behavioral scoring). Everything downstream reuses these instead of
recomputing the same joins with slightly different logic.

**Reference date.** Recency and "has enough time elapsed" calculations use
`mart_reference_date` = the latest observed `order_date` in the dataset,
not the real system date, so every number is reproducible on re-run.

**Cohort methodology.** Acquisition cohort = `DATE_TRUNC('month', signup_date)`.
`months_since_acquisition` is calendar-month arithmetic (not day division),
so "month 1" always means "the next calendar month" regardless of which
day of the month a customer signed up.

**Retention definition.** A customer is "retained" in month N if they
placed **at least one order** during that calendar month. This is a
**behavioral** definition, not contractual churn - there is no
subscription/cancellation event in this schema, so "not retained" means
"did not order this month," not a proven permanent departure. Month 0 is
the signup month itself; it is **not exactly 100%** here (measured:
95.16% weighted average) because each customer's first order lands 0-3
days after signup, so a small share of late-month signups have their
first order land in the following calendar month - a known edge effect
of calendar-month grain, not a bug.

**Observed LTV.** `customer LTV = cumulative observed orders.order_amount`
- no predictive model. Two versions are reported because they answer
different questions:
- **Lifetime LTV**: all revenue to date. Not comparable across
  campaigns/cohorts of different ages - an older cohort has simply had
  more time to accumulate revenue.
- **90-day LTV**: revenue in the first 90 days after signup, computed
  only for customers whose 90-day window has fully elapsed as of the
  reference date (younger customers are excluded from the average, not
  included with an artificially truncated number). This is the fairer
  metric for comparing campaigns head-to-head.

**RFM segmentation.** Recency (days since last order), Frequency (order
count), Monetary (total revenue) are each split into quintiles with
`NTILE(5)` (score 5 = best on that dimension). Segments (Champions,
Loyal, At Risk, Lapsed, New, Needs Attention) are assigned by a top-to-bottom
`CASE` so every customer lands in exactly one segment - see
`sql/04_marts/mart_customer_rfm.sql` for the exact rule for each segment.
No pre-existing churn/quality label is used anywhere in this scoring.
Each `NTILE` call includes `customer_id` as an explicit tiebreaker - with
thousands of customers sharing the same recency/frequency/monetary value,
`NTILE`'s bucket assignment for tied rows is otherwise unspecified by
Postgres and was observed to shift segment counts by roughly 1% between
two loads of byte-identical data before this fix (caught during Phase 4
Docker reproducibility testing).

**LTV:CAC.** Computed at **channel/campaign grain only** - never
per-customer, since CAC is a channel/campaign-level cost, not something
an individual customer incurs. `ltv_cac_lifetime` = avg lifetime LTV per
customer ÷ CAC; at this grain it is **mathematically identical to
`roas_lifetime`** (same revenue window, same customer-count denominator
cancels algebraically) - documented explicitly rather than presented as
two independent numbers. `ltv_cac_90d` uses the 90-day LTV instead and is
**not** equivalent to any ROAS figure - it's the fair, apples-to-apples
comparison across campaigns of different ages. The commonly-cited "3x is
healthy" threshold is labeled as an **external heuristic**, not a
conclusion drawn from this data.

**Profitability.** Extends Phase 2's marketing contribution with LTV and
LTV:CAC side by side, always keeping the acquisition-window and observed-
lifetime numbers in separate, labeled columns so they can't be silently
mixed.

**Budget allocation framework.** A directional classification
(`sql/05_metrics/budget_allocation.sql`), not a proof of an optimal
allocation and not a forecast - it labels each channel `Scale candidate`
/ `Maintain / monitor` / `Review` / `Reduce / investigate` from
marketing-contribution sign, the LTV:CAC heuristic thresholds, and CAC
relative to the dataset's own spend-weighted average CAC (the CAC
comparison is data-driven; the LTV:CAC thresholds are the external
heuristic noted above). Month-3 channel retention is shown for context on
each row but does not independently drive the label, since retention data
is thinner for more recently-launched campaigns.

## Data Validation

- `sql/06_validation/001_data_quality_checks.sql` (Phase 2): 25 checks
  covering primary-key uniqueness, required-field nulls, foreign-key/
  orphan checks, non-negative spend, positive order amounts, campaign
  date sanity, lead/conversion consistency, order date ≥ signup date, and
  cross-level totals reconciliation. **All 25 pass.**
- `sql/06_validation/002_phase3_validation.sql` (Phase 3): 11 checks
  covering cohort membership uniqueness, retention rate ≤ 100%, cohort-
  size reconciliation, RFM one-row-per-customer and no-null-input checks,
  segment-count reconciliation, LTV reconciliation against raw order
  revenue (both overall and channel-level), and LTV:CAC/profitability
  totals reconciling against the Phase 2 marts. **All 11 pass.** Two
  additional informational (non-boolean) checks report Month 0 retention
  (95.16%, expected deviation explained above) and confirm campaigns with
  zero acquired customers - if any existed - resolve to `NULL` CAC/LTV:CAC
  rather than a divide-by-zero error (none currently exist in this
  dataset, so the guard is present but unexercised).

## Current Phase 3 Results (from the synthetic dataset)

Channel-level lifetime LTV:CAC ranges from **2.46 (Affiliate)** to
**84.29 (Organic Search)**; the 90-day (fair-comparison) version ranges
from **1.47 (Affiliate)** to **44.64 (Organic Search)** - same ranking,
smaller spread, as expected once the "more time to accumulate revenue"
effect is removed. Month-1 retention ranges from **~15% (Affiliate)** to
**~24% (Email)**. RFM segmentation splits the 25,064 customers into 6
segments; Champions (20.3% of customers) hold **35.6% of total observed
revenue**, Lapsed (21.5% of customers) hold only **8.7%**.
Budget-allocation framework currently labels **Email, Organic Search, and
Referral as "Scale candidate"**, and **Paid Search, Paid Social, and
Affiliate as "Maintain / monitor"** - no channel is currently unprofitable
in this dataset (all six have positive marketing contribution).

## Phase 4: Power BI Dashboard & Reproducibility

**Dashboard.** A 3-page dashboard design (`powerbi/DASHBOARD_BUILD_GUIDE.md`)
turns the validated SQL into a compact business story: **Page 1 (Executive
Overview)** - 6 KPI cards (revenue, spend, ROAS, CAC, LTV, marketing
contribution - LTV:CAC deliberately omitted as a 7th card since it's
numerically identical to ROAS at this grain), a revenue-vs-spend trend
line, and a contribution-by-channel bar chart. **Page 2 (Channel &
Campaign Performance)** - a 6-row channel table carrying the Scale/
Maintain/Review/Reduce recommendation, a CAC-vs-LTV scatter, and a
40-row campaign detail table. **Page 3 (Customer Cohorts &
Segmentation)** - a cohort retention matrix (heatmap via conditional
formatting), a retention-by-channel line chart, and two RFM segment bar
charts (customer count and revenue share).

Every visual binds directly to one of 7 flat SQL views/marts in
`sql/07_powerbi/` (plus `mart_channel_retention` from Phase 3) - no
metric is redefined or recomputed in Power BI. Only 5 DAX measures exist
in the whole dashboard, all one-line `SUM`/`DIVIDE` aggregations needed
for slicer interactivity (a plain column average of a ratio like CAC
would be mathematically wrong across a multi-channel selection); every
other field is a direct column already computed correctly in SQL.

**Why a build guide instead of a finished dashboard file.** A
hand-authored Power BI Project (`.pbip`) was attempted first, with a full
TMDL semantic model (all 7 tables/views, correctly typed, connected via
`PostgreSQL.Database("localhost:5432","roas")`) and a 3-page PBIR report.
The semantic model design is sound, but Power BI Desktop's project-file
format requires internal manifest files that aren't part of any
available documentation, and the report failed to open
(`Cannot find file 'version.json'`, confirmed by actually launching Power
BI Desktop against it). Rather than ship a broken file or keep
reverse-engineering an undocumented format by trial and error, the
dashboard is handed off as a precise, page-by-page/visual-by-visual spec
instead - every field, chart type, and the 5 DAX formulas are specified
exactly, so building it in the GUI is a ~20-30 minute mechanical exercise
with no analytical decisions left to make.

**Docker / reproducibility.** `docker-compose.yml` + `setup.sh` (both from
Phase 2) were re-verified in Phase 4 with a full clean-slate test: `docker
compose down -v` (removes the container and volume entirely) followed by
`./setup.sh` reproduced the identical schema, dataset, views, and a
36/36 passing validation suite from nothing. No changes to the Docker
setup were needed. During this reproducibility test, a real determinism
bug was found and fixed - see the RFM tiebreaker note above.

Kept out of Phase 4 on purpose (already evaluated and rejected in Phase
1): Kubernetes, Kafka, Airflow, dbt, CI/CD, cloud deployment.
